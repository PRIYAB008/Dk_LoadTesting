# Codebase Review

Reviewed: 2026-09-16  
Scope: current working tree; static review of the k6 flows, scenarios, helpers,
configuration, reporting scripts, and saved k6 summaries. This review does not
exercise the remote API or create any QA records.

## Overall assessment

The project has a clear role-based layout, useful endpoint-level metrics,
payment safeguards, and a reporting/threshold-gate workflow. It is not yet a
reliable load-testing suite: several scenarios conflict with the documented QA
rate limits, and a malformed base URL can be reported as a successful API call.
Address the critical and high-priority findings before using the results for
capacity decisions.

## Findings

| Priority | Finding | Evidence | Impact and recommendation |
| --- | --- | --- | --- |
| Critical | A non-JSON `2xx` response is treated as a successful write. | `utils/helpers.js:30` returns `true` when JSON parsing fails. `config/config.js:3-7` explicitly documents that a trailing slash can return the React HTML page with HTTP 200. | A bad `BASE_URL` can produce green checks and success metrics while no API action occurred. Fail an unexpected non-JSON response (allow an explicit `204` where applicable), validate the response `Content-Type`, and normalize `BASE_URL` once with trailing slashes removed. |
| Critical | A plaintext actor password is committed in the current working tree. | `data/actors.js:10` defaults `ACTOR_PASSWORD` to `Test@1234`, while `README.md:5-13` says no passwords are stored. | Treat the password as exposed: rotate it, remove the default, and pass credentials only through environment variables or the CI secret store. This finding includes the current uncommitted change shown by `git diff`. |
| High | Several load scenarios violate the repository's own login/rate-limit model. | `docs/IMPLEMENTATION_ORDER.md:28-30` requires login once in `setup()`. `scenarios/clientLoad.js:19-21` logs in every iteration. `scenarios/e2eLoad.js:31-37,57-68` logs in per iteration while ramping to 300 VUs. | Results will primarily measure login throttling and may create a large volume of real QA records. Move authentication to `setup()` and share tokens for genuine load tests. Keep the end-to-end scenario at one VU (or make it an explicitly opt-in functional scenario), rather than a 300-VU ramp. |
| High | The journey continues after failed dependent state transitions. | `scenarios/journeyLoad.js:76-78`, `scenarios/steadyLoad.js:172-178`, and `scenarios/e2eLoad.js:110-124` call accept, activate, and follow-on mutations without checking each result. `track()` records a failure but flow functions return no success state. | A failed acceptance or activation can be followed by writes against an invalid contract state, adding noise and side effects to both QA data and metrics. Return `ok` from each flow (or evaluate `isWriteOk(response)`) and stop the iteration immediately when a required transition fails. Mark it as an incomplete journey. |
| High | `adminLoad.js` is a no-op that can look like a valid scenario. | `scenarios/adminLoad.js:1-8` imports the admin flow but its default function makes no request and has no thresholds. | A successful run has no test value and can mislead CI/users. Remove it until implemented, or implement setup/login, the admin request, success metrics, and thresholds. |
| Medium | Account configuration is duplicated and produces inconsistent test identities. | Most scenarios use `data/testData.js`; `e2eLoad.js:3,58-61,76-79` uses `config/config.js`'s `USERS`; journey/steady tests use `data/actors.js`. The default email pairs differ. | The same named operation can target different users/environments, complicating comparison and cleanup. Consolidate account selection in one module, with environment-variable overrides and role-specific validation. |
| Medium | The default journey ramp exceeds the documented clean API ceiling. | `README.md:51-63` estimates a 3–4 VU ceiling for seven-request journeys. `scenarios/journeyLoad.js:12-16` ramps to 50 VUs; `scenarios/e2eLoad.js:33-36` ramps to 300. | The load tests are configured to produce known 429-driven failure rather than a clean baseline. Separate a QA-safe profile from an intentional throttle/limit-discovery profile, and require explicit selection of the latter. |
| Medium | Stored results already demonstrate failed and incomplete test evidence. | Running `node scripts/check-thresholds.js` found 14 breached thresholds in `journeyLoad.json`/`steadyLoad.json` and 10 unverified thresholds in `steadyLoad.json`. | Do not treat the saved reports as a passing baseline. In CI, gate only the result generated by the current run (as the script itself recommends), retain the failure artifacts, and investigate the authentication failure before comparing endpoint latency. |

## Positive observations

- Endpoint-level `Trend`, `Rate`, and `Counter` metrics make failures easier to
  localize than relying only on global HTTP metrics.
- The custom summary and `check-thresholds.js` correctly flag thresholds that
  matched zero samples instead of accepting k6's default green result.
- Payment creation is guarded by `ALLOW_PAYMENT=true`, and the documentation
  correctly distinguishes order creation from a settled hosted checkout.
- All 25 scenario files pass `k6 inspect`, so the current scripts are
  syntactically valid for k6.

## Recommended remediation order

1. Rotate/remove the committed actor password and normalize/validate the base
   URL and response content type.
2. Correct authentication lifecycle and VU profiles; make destructive,
   end-to-end runs single-VU and explicitly opt-in.
3. Stop dependent flows after the first failed state transition, and report an
   incomplete journey separately from a successful one.
4. Implement or remove `adminLoad.js`, then unify test-account configuration.
5. Re-run the QA-safe profile, archive its exact JSON summary, and use that
   single file with `node scripts/check-thresholds.js <result.json>` in CI.
